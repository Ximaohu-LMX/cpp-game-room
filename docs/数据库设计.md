# 数据库设计

本项目采用吃鸡式单胜者对战背景：每个房间开启一局 battle，一局游戏只有一个最终胜者，其他参与玩家均为失败方。当前代码实现的是简化战斗流程，用移动、攻击、血量和存活判断模拟战斗，不实现完整商业游戏中的地图、装备、子弹、技能、安全区、回放等复杂玩法。

## MySQL 与 Redis 分工

项目同时使用 MySQL 和 Redis。

MySQL 负责最终持久化数据：

- 玩家基础数据
- 玩家最终积分
- 玩家累计胜负
- 战斗总记录
- 每个玩家在一局战斗中的结果
- 结算日志和幂等控制

Redis 负责实时排行榜视图：

- 使用 Sorted Set 保存玩家积分排名
- 支持快速查询排行榜 TopN
- 作为 MySQL 中 `player.score` 的查询加速视图

整体关系是：

```text
MySQL 是最终数据来源
Redis 是排行榜缓存和读加速
```

战斗结算时，服务端先通过 MySQL 更新玩家积分和结算日志，再把玩家最新积分写入 Redis 排行榜。Redis 数据如果丢失，可以通过 MySQL 的 `player` 表重建。

## MySQL 表设计

### player

玩家表，保存玩家基础数据和累计战绩。

| 字段 | 说明 |
| --- | --- |
| player_id | 玩家 ID，主键 |
| name | 玩家名 |
| score | 积分，默认 1000 |
| win_count | 胜场数 |
| lose_count | 败场数 |
| create_time | 创建时间 |
| update_time | 更新时间 |

### battle

战斗总表，一场 battle 一条记录。

| 字段 | 说明 |
| --- | --- |
| battle_id | 数据库自增战斗 ID，主键；同一局重试复用 |
| room_id | 房间 ID |
| winner_id | 本局唯一胜者 |
| start_time | 开始时间，当前预留 |
| end_time | 结算事务成功时写入的结束时间 |
| result_json | 战斗结果扩展字段 |
| settled | 0 表示预留或尚未提交，1 表示整局结算已提交 |

### battle_player_result

战斗玩家结果表，一场 battle 中每个参与玩家一条记录。

| 字段 | 说明 |
| --- | --- |
| result_id | 自增主键 |
| battle_id | 战斗 ID |
| player_id | 玩家 ID |
| result | 本局结果，WIN 或 LOSE |
| score_delta | 本局积分变化 |

唯一键：

```sql
UNIQUE KEY uniq_battle_player_result (battle_id, player_id)
```

该唯一键保证同一场战斗中，同一个玩家只有一条结果记录。

### settlement_log

结算日志表，用于保证积分结算幂等。

| 字段 | 说明 |
| --- | --- |
| settlement_id | 数据库自增结算日志 ID |
| battle_id | 战斗 ID |
| player_id | 玩家 ID |
| score_delta | 积分变化 |
| created_at | 创建时间 |

唯一键：

```sql
UNIQUE KEY uniq_battle_player (battle_id, player_id)
```

该唯一键保证同一场战斗中，同一个玩家只有一条结算日志；积分更新的幂等还依赖固定 battle_id 和 MySQL 事务。

## Redis 数据结构设计

当前 Redis 只用于排行榜。

### rank:score

排行榜 key：

```text
rank:score
```

数据类型：

```text
Sorted Set
```

成员和值：

```text
member = player_id
score  = 玩家当前积分
```

示例：

```redis
ZADD rank:score 1020 1001
ZADD rank:score 980 1002
ZADD rank:score 1100 1003
```

查询排行榜时使用：

```redis
ZREVRANGE rank:score offset stop WITHSCORES
```

`ZREVRANGE` 会按积分从高到低返回玩家列表。

当前 Redis 不保存：

- battle 记录
- 玩家每帧输入
- 战斗状态快照
- 结算日志
- 玩家完整资料

如果 Redis 中的排行榜数据丢失，可以从 MySQL 重建：

```text
SELECT player_id, score FROM player;
-> ZADD rank:score score player_id
```

## 未落库的战斗内数据

当前数据库只持久化玩家基础数据、战斗最终结果、每个玩家的胜负结果、积分结算日志和排行榜数据。

以下战斗内过程数据没有落库：

- 玩家每一帧输入
- 每一帧状态快照
- 移动轨迹
- 攻击过程明细
- 伤害明细
- 死亡时间线
- 战斗回放数据

这些数据目前只在服务端内存中参与 tick 推进。流程是：

```text
InputRequest
-> InputBuffer
-> GameLoop 50ms tick 消费输入
-> GameRoom 更新位置、血量、存活状态
-> StateSync 广播状态快照
```

因此，当前版本能跑通“匹配 -> 房间 -> 简化战斗 -> 胜负判断 -> 结算 -> 排行榜”的主链路，但不支持基于数据库的战斗回放、操作审计或完整反作弊分析。

## room_id 与 battle_id

`room_id` 表示房间 ID，是玩家匹配后进入的房间实例。

`battle_id` 表示战斗 ID，是一局具体对战和结算的唯一标识。

当前项目中，一个 room 只打一局 battle，打完后房间关闭，所以两者看起来是一一对应的。但概念上不合并，方便后续扩展：

- 一个房间连续打多局
- 房间重开
- 观战房间
- 自定义房间

## 一场战斗的数据库操作流程

战斗首次进入结算时，由数据库自增分配 battle_id 并预留 battle 记录，同一局后续重试复用该 ID。

在一个 MySQL 事务中：

1. SELECT ... FOR UPDATE 锁定 battle 行。
2. 如果 settled 已为 1，核对房间、胜者和所有玩家结果；一致则按成功重试处理，冲突则拒绝。
3. 如果尚未结算，写入所有玩家的 battle_player_result 和 settlement_log，并更新 player.score、win_count、lose_count。
4. 写入 winner_id、end_time 和 settled = 1，然后提交。任一步失败都回滚整局修改。

提交后再读取 MySQL 中的当前积分，用 ZADD 刷新 Redis 榜单。Redis 失败会触发同一 battle_id 的重试，重复请求只补做榜单刷新，不再次加减分。

房间在结算和刷新成功前保持 Settlement 状态，每秒尝试一次；期间不允许 ready 请求重新开局。

## 为什么唯一键还需要事务

只有 (battle_id, player_id) 唯一键时，可能发生“日志成功、积分更新失败”。如果随后把重复日志当作成功结算，玩家会永久漏加分。

当前实现将日志、战绩、积分和完成标志放在同一个 InnoDB 事务中，并在事务期间持有数据库连接锁。事务失败时这些修改一起回滚；提交响应丢失后，调用方复用原 ID 查询完成标志并安全重试。

完整说明、已有数据库迁移和测试见 [战斗结算幂等](settlement_idempotency.md)。当前没有持久化重试队列，进程崩溃后不会自动恢复未提交的内存战斗。

## 总结

```text
battle 记录一局游戏整体结果
battle_player_result 记录每个玩家在本局中的胜负和积分变化
固定 battle_id、事务、行锁与 settlement_log 唯一键共同保证结算幂等
player 保存最终玩家积分和累计胜负
Redis ZSET 保存排行榜实时视图
```
